# КОНТУР: сервер для VPS

Этот комплект запускает веб-игру, комнаты и метрики на одном VPS. Внутри — готовая сборка Node.js 24, SQLite, HTTPS через Caddy и резервное копирование. Устанавливать pnpm, компилировать игру и настраивать Cloudflare D1 на VPS не нужно.

Для первого теста подойдёт Linux VPS с 1 CPU, 1 ГБ RAM и SSD; 2 ГБ дадут больше запаса системе и обновлениям. Число одновременных игроков определим нагрузочным тестом на арендованном сервере. Здесь один процесс игры: несколько копий сервера и балансировщик пока не настраиваем.

## Запуск с доменом

1. Установите Docker Engine и Docker Compose plugin по официальной инструкции для [Ubuntu](https://docs.docker.com/engine/install/ubuntu/) или [Debian](https://docs.docker.com/engine/install/debian/). Проверьте `docker version` и `docker compose version`. Команды ниже выполняются пользователем с доступом к Docker; при необходимости запускайте скрипты через `sudo sh`.
2. Направьте A-запись поддомена, например `game.example.com`, на IPv4 VPS. AAAA добавляйте только при рабочем IPv6. Если DNS находится в Cloudflare, для первого запуска выберите **DNS only**. Откройте входящие TCP 80 и 443, UDP 443 по желанию; SSH оставьте доступным для администрирования. Порт 8080 наружу не открывайте.
3. Распакуйте архив в постоянный каталог, например `/opt/perimeter`, и перейдите в него. Выполните, подставив свой домен и email:

```sh
sh deploy/setup.sh game.example.com admin@example.com
sh deploy/manage.sh start
sh deploy/manage.sh status
sh deploy/manage.sh health
```

Откройте `https://game.example.com` на двух устройствах. Caddy получает и обновляет сертификат автоматически; DNS должен уже указывать на сервер, а порты 80/443 быть доступны. Первое скачивание Docker-образов требует интернета.

`setup.sh` создаёт `deploy/.env` с правами 600 и случайным ключом владельца для экспорта метрик. Не отправляйте этот файл в GitHub или игрокам. Повторный запуск не перезаписывает настройки. `start` создаёт Docker-образ из готовых файлов, запускает сервисы и сохраняет данные в Docker-томах. После перезагрузки VPS сервисы поднимаются автоматически.

## Если домена пока нет

Можно проверить сервер через SSH-туннель, не выставляя незашифрованную игру в интернет:

```sh
# На VPS, в каталоге распакованного архива:
sh deploy/setup.sh --local
sh deploy/manage.sh --local start
sh deploy/manage.sh --local health
```

```sh
# На своём компьютере; замените user и VPS_IP:
ssh -N -L 8080:127.0.0.1:8080 user@VPS_IP
```

Откройте `http://127.0.0.1:8080` в двух профилях браузера. Это локальный тест: Caddy не запускается, порт VPS доступен только через loopback, Android-релиз требует настоящий HTTPS-адрес. Для всех команд управления таким запуском добавляйте `--local` перед командой.

Для перехода на домен остановите локальный запуск, измените только `DOMAIN` и `ACME_EMAIL` в `deploy/.env`, сохранив ключ, настройте DNS и выполните обычный `sh deploy/manage.sh start` без `--local`.

## Проверка игры

- Первый игрок создаёт комнату, второй подключается по ссылке/коду. Оба расставляют сеть и нажимают «Готов»; затем начинается матч.
- Оба делают ходы. Обновление страницы и краткое отключение сети должны возвращать игрока на его место.
- Создайте открытую комнату и проверьте поиск со второго профиля; закрытие комнаты владельцем должно вывести обоих из неё.
- Во время матча выполните `docker compose --env-file deploy/.env -f deploy/compose.yml restart app`. После восстановления соединения матч должен продолжиться. Для локального режима добавьте `-f deploy/compose.local.yml` перед `restart`.
- Выгрузите метрики командой ниже и проверьте записи о создании комнаты, старте и ходах.

Тесты сборки и локальные проверки не заменяют этот проход на реальном VPS и двух телефонах.

## Управление и метрики

```sh
sh deploy/manage.sh status
sh deploy/manage.sh health
sh deploy/manage.sh logs
sh deploy/manage.sh metrics metrics.json
sh deploy/manage.sh stop
sh deploy/manage.sh start
```

`health` проверяет и API, и доступность БД; ожидаемый ответ содержит `"ok":true` и `"storage":"ready"`. `logs` выводит последние строки, не включая ключ владельца. Docker ограничивает журналы каждого сервиса тремя файлами по 5 МБ.

`metrics.json` — файл для анализа и передачи разработчику. Скрипт обращается к закрытому экспорту из контейнера; ключ не попадает в командную строку или файл. Экспорт содержит обезличенные идентификаторы матчей и события, без ключей мест игроков и скрытых расстановок. Доступны последние 30 дней; один экспорт ограничен 100 матчами и 5000 событиями. Если `truncated:true`, для полного анализа нужны выгрузки меньших диапазонов через `/api/metrics/export?since=...&until=...` с ключом владельца. Не отправляйте вместо экспорта полную SQLite-базу: в ней есть состояние комнат.

## Резервные копии и восстановление

Копия SQLite создаётся сразу после запуска сервиса резервирования и затем каждые 6 часов через штатный online backup API. Проверяется целостность снимка; сохраняются последние 28 копий (примерно 7 дней при непрерывной работе). Настройки `BACKUP_INTERVAL_HOURS` и `BACKUP_KEEP` находятся в `deploy/.env`. Это локальные копии на том же VPS; для защиты от потери диска копируйте их и `deploy/.env` в отдельное закрытое хранилище.

```sh
sh deploy/manage.sh backup
sh deploy/manage.sh snapshots
# Скопировать выбранную копию с Docker-тома в текущий каталог VPS:
docker compose --env-file deploy/.env -f deploy/compose.yml cp backups:/backups/perimeter-YYYY-MM-DDTHH-MM-SS-mmmZ.sqlite ./
```

Восстановление откатывает комнаты и метрики к выбранному снимку. Выберите точное имя из `snapshots`, предупредите тестировщиков и выполните:

```sh
sh deploy/manage.sh restore perimeter-YYYY-MM-DDTHH-MM-SS-mmmZ.sqlite
sh deploy/manage.sh health
```

Скрипт останавливает игру и резервирование, проверяет снимок, сохраняет текущее состояние как `before-restore-*.sqlite`, заменяет БД и запускает сервисы. При ошибке восстановления сервер остаётся остановленным — смотрите сообщение, не удаляйте исходные файлы. Снимки `before-restore-*` не удаляются автоматически. Для возвращения копии с другого сервера сначала поместите её в `/backups` контейнера `backups`, затем используйте `restore`.

**Не выполняйте `docker compose down -v`: это удалит тома с комнатами, метриками, копиями и сертификатами.** Обычная остановка и обновление их сохраняют.

## Обновление

Сначала сделайте резервную копию. Распакуйте новую сборку в тот же каталог поверх старой, сохранив `deploy/.env`, и выполните `sh deploy/manage.sh start`. Новая версия пересоздаст контейнер с тем же томом данных; миграции БД применяются один раз автоматически. Обновление прерывает соединение на время перезапуска, после чего клиенты опрашивают сервер снова. Для отката схемы нужна совместимая старая сборка и снимок БД до обновления.

## Подключение APK и переход с Cloudflare

Игроки веб-версии на этом домене используют API того же VPS. Для Android нужно вписать этот же HTTPS-origin в `mobile/config.json` (`onlineOrigin`) и пересобрать подписанный APK. CORS для `https://appassets.androidplatform.net` уже предусмотрен; Android и браузер смогут играть в общих комнатах.

Существующий сайт `*.workers.dev` продолжает работать со своей D1-базой. Его комнаты и старые метрики сюда автоматически не переносятся. Для первого теста все участники должны открывать новый адрес VPS; одинаковый код комнаты на разных серверах не соединяет игроков. Отдельный фронтенд на Cloudflare потребует явного подключения к VPS API и настройки разрешённого origin.

Сервер сохраняет текущий HTTP polling; WebSocket-переход не требуется для первого теста. Суточной квоты Cloudflare здесь нет: фактический предел зависит от VPS, размера БД и числа игроков. Ограничения `API_REQUESTS_PER_MINUTE=600` и `ROOM_ADMISSIONS_PER_MINUTE=12` защищают от частых запросов **с одного IP**, а не задают общую ёмкость сервера. За одним NAT игроки делят этот лимит; менять его следует по метрикам.

## Состав комплекта

`server.mjs` — серверный bundle; `public/` — веб-игра; `drizzle/` — миграции; `deploy/` — Docker, HTTPS и команды администрирования. Сборка не содержит реальных ключей, БД, сертификатов или тестовых комнат. Backend не публикует порт напрямую; Caddy передаёт фактический адрес клиента через изолированную Docker-сеть, подставленные клиентом forwarding-заголовки не используются.
