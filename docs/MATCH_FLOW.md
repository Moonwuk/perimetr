# Сетевая партия: готовность, выход и восстановление соединения

Правила общие для Cloudflare/D1 и VPS/SQLite. Размер поля, экономика и набор карт не меняются.

## Начало

- В комнате два независимых места с отдельными ключами восстановления.
- Подключение второго игрока переводит комнату из `waiting` в `setup`.
- Партия начинается только после подтверждения расстановки обоими игроками. `players[].ready` показывает, кто уже готов; подтверждённую расстановку нельзя менять.
- При переходе в `playing` сервер сохраняет `game.startedAt`. Долгое ожидание в лобби не сокращает период восстановления после старта.
- Рекомендованная расстановка использует обычное действие `deploy` с теми же проверками пяти разных клеток и четырёх жетонов защиты. Обхода серверной проверки для быстрого старта нет.

## Выход и завершение

| Состояние | Допустимый исход |
| --- | --- |
| `waiting` / `setup` | Хозяин может закрыть комнату; победитель не назначается |
| `playing` | Закрытие комнаты запрещено. Любой участник может сдаться, в том числе вне своего хода |
| `finished` | Результат окончателен; хозяин может закрыть комнату, сохранив результат в метриках |

Сдача сохраняет `finishReason: "surrender"`, окончание по экономическим правилам — `"score"`, техническая победа — `"disconnect"`. Поле необязательное для совместимости со старыми сохранениями. Реванш требует двух голосов, получает следующий `matchNumber`, новую расстановку и другой первый ход. Причина финала, пауза и отметки старта/возобновления предыдущей партии в реванш не переходят.

Закрытие проверяет ревизию и статус непосредственно в SQL. Если второй игрок успел подтвердить готовность или состояние комнаты изменилось, сервер возвращает `409` с новым состоянием: начавшийся матч нельзя удалить устаревшей командой.

## Обрыв связи

Ответ комнаты содержит `serverTime`, `presence: [hostSeenAt, guestSeenAt]` и `reconnectGraceMs: 120000`. Опрос обновляет присутствие не чаще одного раза в 15 секунд; подтверждённый игровой ход также обновляет присутствие участника.

Предел восстановления для соперника:

```text
max(presence[opponent], game.startedAt ?? 0, game.resumedAt ?? 0) + reconnectGraceMs
```

Счётчик интерфейса опирается на время сервера и прошедшее время с получения ответа, а не на часы телефона. При потере собственного соединения нельзя обещать актуальность статуса соперника. Уход приложения в фон также может остановить опрос: нужно вернуться в игру в пределах этого периода.

По окончании периода оставшийся участник может запросить техническую победу. Автоматического поражения по одному таймеру нет. Если оба участника пропали, сервер не назначает победителя; вернувшийся игрок получает сохранённую партию. Истечение срока самой комнаты обрабатывается существующей очисткой, как оставленная партия без победителя.

### API технической победы

`POST /api/rooms`, заголовок `Authorization: Bearer <ключ своего места>`:

```json
{"intent":"claimDisconnect","code":"ABCDEFG","revision":3}
```

- `200`: обычный ответ комнаты, `game.status: "finished"`, `winner` — заявитель, `finishReason: "disconnect"`.
- `409`: матч ещё не начался/уже окончен, период не истёк, соперник вернулся или ревизия изменилась; актуальное состояние возвращается, если комната существует.
- `403`: нет доступа к месту игрока.
- `404`: комната закрыта или истекла.

Это отдельное серверное намерение, не игровой `Action`. Клиент не передаёт достоверное время, победителя или срок восстановления. SQL одновременно проверяет ревизию, статус и отметку присутствия соперника: обновление присутствия не меняет ревизию, поэтому одной проверки ревизии недостаточно. Из гонки «ход / переподключение / заявка» сохраняется допустимый результат; повторный запрос не назначает второго победителя.

## Пауза по взаимному согласию

Один участник запрашивает паузу, второй принимает или отклоняет её. Запросивший может отменить свой запрос. Пока ответ не получен, игра продолжается: нельзя остановить чужой ход одним запросом.

После принятия оба видят `game.pause: { requestedBy, pausedAt }` с серверной отметкой времени. До принятия `pausedAt` равен `null`. На согласованной паузе карты, завершение хода, добор и другие игровые действия запрещены самим движком; деньги, очки действия, очередь хода и сети не меняются. Сдаться всё ещё можно. Закрыть активную партию или получить техническую победу за отсутствие соперника нельзя.

Любой участник может продолжить согласованную паузу. Сервер удаляет `pause` и сохраняет `game.resumedAt`: с этого времени у каждого участника снова есть 120 секунд для восстановления соединения. Повторная команда продолжения уже активной игры отклоняется и не продлевает период. Согласование новой паузы опять требует двух участников.

`POST /api/rooms`, тот же ключ места и актуальная ревизия:

```json
{"intent":"pause","decision":"request","code":"ABCDEFG","revision":3}
```

| `decision` | Кто может отправить | Условие |
| --- | --- | --- |
| `request` | Любой участник | Идёт матч, запроса и паузы ещё нет |
| `accept` / `decline` | Соперник запросившего | Запрос ожидает ответа |
| `cancel` | Запросивший | Запрос ожидает ответа |
| `resume` | Любой участник | Пауза уже принята |

Успех — `200` и обычное состояние комнаты. Несовместимое состояние, чужая роль или устаревшая ревизия — `409`; неизвестное значение команды — `400`. Изменения паузы записываются через ту же атомарную проверку ревизии, что и ходы. Одновременные «принять / отменить / сделать ход» не могут сохранить два перехода из одной ревизии. События паузы записываются в серверные метрики; они не учитываются как трата денег или действий. Продолжительность матча в экспорте остаётся календарной и включает паузу.

**Пауза не продлевает срок жизни комнаты: он остаётся 24 часа с создания.** Состояние паузы хранится вместе с матчем и переживает перезапуск VPS в пределах этого срока. Завершение партии очищает активную или ожидающую паузу.

## Проверка

```bash
node --experimental-strip-types --test tests/rooms.test.mjs tests/server-metrics.test.mjs tests/api-cors.test.mjs
pnpm vps:build
pnpm vps:test
pnpm cf:build
pnpm cf:test
```

Модульные тесты проверяют отказ преждевременной заявки, старт после долгого лобби, конкуренцию заявки с ходом и присутствием, запрет закрытия во время старта, неизменность финала, сохранение причины в метриках и отсутствие утечки скрытой руки/расстановки.

HTTP-проверки используют два независимых ключа игроков и настоящий сервер. Проверка VPS дополнительно останавливает сервер, состаривает только временную тестовую SQLite, запускает сервер заново, отправляет две конкурентные заявки и проверяет единственный исход в экспорте после закрытия комнаты и повторного запуска. Отдельный перезапуск во время согласованной паузы проверяет её сохранение; после продолжения оба клиента видят неизменные ресурсы и новую отметку `resumedAt`. Это контролируемая имитация истечения периода без двухминутного ожидания в CI; в рабочем API возможности изменять время присутствия нет.

При ручном тесте на двух телефонах: подтвердить готовность по очереди, закрыть соединение одного устройства, проверить счётчик на другом, вернуть первое до окончания периода; затем повторить с истечением периода и явной заявкой. Проверить результат на обоих устройствах и попытку закрыть активную комнату. Техническая победа и добровольная сдача должны иметь разные объяснения финала.

Для ручной проверки паузы: попросить её первым устройством; убедиться, что до согласия второго можно сделать ход. Затем принять, проверить блокировку карт и технической победы, перезапустить страницу и продолжить любым участником. Деньги, действия и очередь хода должны сохраниться, таймер восстановления — начаться заново.
